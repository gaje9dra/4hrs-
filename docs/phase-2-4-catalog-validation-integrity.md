# Phase 2.4 — Catalog Validation, Pricing Rules & Product Integrity

## Scope

Phase 2.4 adds reusable canonical catalog validation and integrity rules on top of the Phase 2.2 catalog and Phase 2.3 inventory foundation.

Implemented:

- Product validation
- Product Variant validation
- SKU validation
- Slug validation
- Price and compare-at-price validation
- Currency validation
- Variant duplicate detection
- Category validation and hierarchy checks
- Collection validation
- Tag normalization/validation
- Image metadata and ownership validation
- Primary-image validation
- Publishing-readiness validation
- Product lifecycle transition rules
- Catalog relationship duplicate checks
- Effective variant pricing
- Focused automated tests
- Database integrity constraints

No provider, order, checkout, payment, shipping, admin UI, or synchronization functionality is included.

## 1. Validation layers

The catalog follows:

```text
Input
  ↓
Catalog validation
  ↓
Application service
  ↓
Repository
  ↓
Database
```

Application validation catches actionable input errors before persistence. Database constraints remain authoritative for fundamental integrity such as uniqueness, foreign keys, monetary validity, and image ownership.

The project had no existing validation framework, so this phase intentionally adds no validation dependency. Reusable validation lives in:

`lib/catalog/validation.ts`

## 2. Product validation

Required structural rules:

- title must contain non-whitespace content
- title normalization trims leading/trailing whitespace and collapses accidental internal whitespace
- intentional capitalization is preserved
- slug must use the canonical lowercase URL-safe format
- status must be DRAFT, ACTIVE, or ARCHIVED
- currency must be a three-letter uppercase code
- selling price must be non-negative and have at most two decimal places
- compare-at price is optional
- compare-at price, when present, must be greater than or equal to selling price

No arbitrary product-name character restrictions are imposed.

Examples such as:

- Oversized Graphic T-Shirt
- Heavyweight Cotton Hoodie
- Classic Oxford Shirt
- Relaxed Fit Cargo Pants

remain valid.

## 3. Slug rules

Canonical format:

`^[a-z0-9]+(?:-[a-z0-9]+)*$`

Examples:

- valid: `oversized-graphic-t-shirt`
- invalid: `Oversized Graphic T-Shirt`
- invalid: `oversized--graphic-shirt`
- invalid: `-graphic-shirt`

Slugs are provider-independent and database-unique.

Explicit slugs are preserved rather than regenerated by validation.

## 4. SKU rules

SKU is store-owned and provider-independent.

Application validation requires:

- trimmed value
- non-empty value

No unnecessary character whitelist is imposed.

Examples:

- `TSHIRT-BLK-M-001`
- `HOODIE-GRY-L-004`
- `CAP-BLK-001`

Database uniqueness remains authoritative.

The validation layer does not invent SKUs.

## 5. Product Variant validation

Every persisted variant must reference a Product through the database foreign key.

Variant validation checks:

- SKU
- status
- optional size
- optional color
- optional display name
- optional price override
- optional compare-at-price override

Size and color are not required for every product.

### Duplicate variant rule

The current Phase 2.2 schema exposes size and color as the structured variant-defining options. Within that current architecture, a duplicate means the same Product has another variant with the same normalized size and color pair.

Normalization:

- trim whitespace
- collapse accidental whitespace
- compare case-insensitively

The rule remains application-level rather than creating a database uniqueness constraint that could incorrectly prohibit future structured option types.

A future option model can replace this key without changing the broader validation boundary.

## 6. Pricing

The canonical money representation remains PostgreSQL/Prisma `DECIMAL(12,2)`.

No second money type or floating-point database field is introduced.

Rules:

- selling price >= 0
- maximum two decimal places at validation boundary
- compare-at price is optional
- compare-at price >= selling price

No discount calculation is implemented.

### Effective variant price

The existing Phase 2.2 inheritance model is preserved:

```text
Product.price
    ↓
Variant price override?
    ↓
Effective catalog price
```

A null variant price inherits Product.price. A non-null variant price overrides it.

Currency remains inherited from Product because ProductVariant has no currency field.

## 7. Currency

Currency is represented consistently as a three-character uppercase value.

The current catalog default remains INR.

This phase does not implement:

- currency conversion
- exchange rates
- multi-currency pricing
- currency APIs

## 8. Image validation

ProductImage must have exactly one owner:

- Product, or
- ProductVariant

It cannot reference both and cannot be detached from both.

Validation checks:

- ownership
- absolute URL/storage reference
- non-negative integer sort order
- primary-image semantics

The database also enforces non-negative sort order.

### Cross-product variant images

A variant-specific image must reference a ProductVariant belonging to the same Product. The reusable `validateImageRelationships()` helper accepts the current Product ID and known variants for this cross-model check.

The database foreign keys guarantee that the referenced ProductVariant itself exists.

### Primary images

A Product may have at most one primary product-level image.

A PostgreSQL partial unique index enforces this rule:

`Product_primary_image_unique`

Variant-specific image ordering remains independent.

## 9. Category validation

Checks:

- non-empty name
- canonical slug
- status
- parent relationship

Database constraints enforce:

- unique slug
- foreign-key integrity
- no direct self-parent
- non-empty name

Application helpers also support category cycle detection for arbitrary hierarchies. A full category graph engine is not introduced.

## 10. Collection validation

Collection remains distinct from Category.

Checks:

- non-empty name
- canonical slug
- status

Database constraints enforce unique slug, foreign-key relationships, and non-empty name.

No category-specific behavior is added to collections.

## 11. Tag validation

Tags use normalized names/slugs at the application boundary:

- names are trimmed and accidental whitespace is collapsed
- logical name comparison is case-insensitive
- slugs are normalized to lowercase before validation
- slug format remains canonical

`validateUniqueNormalizedTags()` detects logical duplicates in an input set, such as:

- Streetwear
- streetwear
-  STREETWEAR

The database's unique slug remains authoritative for persisted identity.

## 12. Junction relationships

ProductCategory, ProductCollection, and ProductTag already use composite primary keys.

This provides database-level duplicate prevention.

The validation layer also exposes `validateJunctionUniqueness()` for reusable pre-persistence validation.

Foreign keys remain the final authority for referenced-record existence.

## 13. Publishing readiness

`validatePublishingReadiness()` answers whether a product is structurally ready to become active.

It does not publish the product and does not change Product.status.

For the current fashion-store architecture, readiness requires:

- valid product fields
- at least one ACTIVE ProductVariant
- valid variant SKU/pricing data
- at least one product-level image
- valid image metadata
- no duplicate variants
- no more than one primary product-level image

The architecture therefore treats a sellable fashion Product as requiring at least one active ProductVariant.

A future product type can explicitly opt out of the variant/image requirement at the validation boundary without introducing a second selling model.

## 14. Product lifecycle

The lifecycle is deterministic:

```text
DRAFT
  ├──> ACTIVE
  └──> ARCHIVED

ACTIVE
  └──> ARCHIVED

ARCHIVED
  └──> ARCHIVED
```

Allowed self-transitions are retained.

ARCHIVED is terminal in this phase. No restore workflow is introduced.

Validation never changes status automatically.

## 15. Error model

Validation errors are structured:

```text
{
  field,
  code,
  message
}
```

Example:

```text
field: price
code: INVALID_PRICE
message: Price must be zero or greater.
```

`CatalogValidationError` can carry the structured issue list for service-layer use.

Database stack traces are not transformed into customer-facing errors here.

## 16. Inventory cross-check

Phase 2.3 remains intact.

Inventory is attached to ProductVariant through the existing foreign key and unique variant relationship.

The catalog layer does not implement:

- reservations
- stock deduction
- checkout
- order creation

SKU identity remains store-owned and independent of inventory/provider identity.

Inventory archival/audit behavior remains governed by Phase 2.3 restrictive relationships.

## 17. Provider-import compatibility

Validation operates on canonical catalog inputs.

Future flow:

```text
Provider Product
      ↓
Mapping / Transformation
      ↓
Canonical Product Input
      ↓
Catalog Validation
      ↓
Canonical Product
```

No Qikink, Printrove, Printful, Printify, or other provider adapter is implemented.

## 18. Manual-product compatibility

The same validation boundary supports future manual catalog input:

```text
Admin Product Input
      ↓
Catalog Validation
      ↓
Canonical Product
```

No admin UI is included.

## 19. Database constraints

Phase 2.2 constraints remain intact, including:

- Product slug uniqueness
- ProductVariant SKU uniqueness
- Category slug uniqueness
- Collection slug uniqueness
- Tag slug uniqueness
- composite junction uniqueness
- ProductImage exactly-one-owner rule
- Category self-parent prevention
- non-negative Product pricing
- compare-at >= selling price
- non-negative variant pricing
- compare-at >= variant selling price when a variant override exists

Phase 2.3 inventory quantity constraints remain intact.

Phase 2.4 additionally enforces:

- Product title is not blank
- ProductVariant SKU is not blank
- ProductImage sort order >= 0
- Category name is not blank
- Collection name is not blank
- Tag name is not blank
- at most one primary product-level image

Migration:

`prisma/migrations/20260928140000_catalog_integrity/migration.sql`

No destructive reset or data wipe is introduced.
