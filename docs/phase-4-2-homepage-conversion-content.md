# Phase 4.2 — Homepage Conversion & Content System\n\n## Scope\nPhase 4.2 refines the existing homepage rather than rebuilding it.\n\nImplementation is limited to homepage conversion/content, reusable heading semantics, shared ProductCard heading hierarchy, canonical homepage catalog selection, tests, and this documentation.\n\nNo cart, wishlist, checkout, payments, orders, shipping, authentication, reviews/ratings, provider-specific logic, or provider storefront branches were added.\n\n## 1. Homepage flow\nThe final flow is:\n1. Hero\n2. Curated product discovery\n3. Shop by category\n4. New arrivals\n5. Shop the collections\n6. Brand/value statement\n7. Final shopping CTA\n8. Existing storefront footer/shell\n\nThe former standalone editorial collection block was removed because it duplicated collection discovery without adding a separate catalog destination.\n\nThe value area is a concise brand statement rather than a service-claim block because the canonical requirements do not provide documented free-shipping, warranty, delivery-speed, satisfaction, or similar policy data.\n\n## 2. Hero\nThe existing Bauhaus hero was refined without rebuilding its composition.\n- Headline remains concise and prominent.\n- Supporting copy remains short and brand-specific.\n- Primary CTA is singular and points to /shop.\n- CTA label is now “Shop the catalog”, making the destination explicit.\n- Hero visual continues to use a real published catalog product when available.\n- If no usable product image exists, the existing geometric fallback is retained.\n- Hero image remains a Next Image with above-the-fold priority loading.\n\nNo vague or dead CTA was introduced.\n\n## 3. Product discovery\nCurated picks remains the primary product-discovery section.\n\nThe source is the first deterministic active collection returned by the canonical collection discovery query. That collection already has at least one published product because the Phase 4.1 repository boundary enforces the published-product existence predicate.\n\nProducts are requested through the existing storefront catalog service using the merchandising sort.\n\nThe shared ProductCard remains the only homepage product-card component.\n\nProduct data is public storefront data: title, canonical slug/link, real primary media when available, real price/currency, valid compare-at price, and public availability state.\n\nNo bestseller, trending, popularity, recommendation, random, AI, or provider-specific ranking was introduced.\n\nNew-arrival products remove curated product IDs to avoid intentional duplication between discovery sections.\n\n## 4. Category discovery\nShop by category uses listActiveCategoriesWithPublishedProducts().\n\nThis is the Phase 4.1 canonical repository boundary and excludes active categories with no published products.\n\nCategory links use categoryPath() and remain canonical catalog URLs.\n\nThe homepage displays up to six categories in deterministic repository order.\n\nNo category image model was invented. Where the canonical category DTO has no image, Bauhaus geometry supplies visual treatment without pretending it is catalog media.\n\n## 5. New arrivals\nNew arrivals uses the existing canonical getStorefrontProducts({ pageSize: 8, sort: "newest" }).\n\nThe query is based on Product createdAt through the catalog sorting layer.\n\nNo isNew field or homepage-specific lifecycle flag was added.\n\nOnly published products reach the public storefront DTO.\n\nPresentation is bounded to four products after curated-product de-duplication.\n\n## 6. Collection discovery\nShop the collections uses listActiveCollectionsWithPublishedProducts().\n\nOnly active collections with at least one published product are eligible.\n\nCollection links use collectionPath().\n\nUp to three collections are displayed in deterministic order.\n\nThe canonical Collection model does not provide collection media, so the homepage uses real collection identity/description plus existing Bauhaus geometric treatment.\n\nNo fake collection image, collection record, or parallel collection-media model was created.\n\n## 7. Brand/value section\nThe homepage now has one concise brand/value block.\n\nThe copy stays within the established 4HRS positioning already used by the hero: bold form, clear color, and a deliberately graphic point of view.\n\nIt does not make unsupported operational or quality claims.\n\nThe section is presentation-only and contains no commerce logic.\n\n## 8. Final CTA\nThe final CTA is a direct shopping continuation.\n\nDestination: /shop\n\nThe CTA uses the established Bauhaus treatment and existing primary button component.\n\nThe wording is action-oriented: Find your next piece. / Browse the live 4HRS catalog. / Shop all.\n\nNo dead-end route or placeholder destination was added.\n\n## 9. Bauhaus design\nExisting design language is preserved: #F0F0F0, #121212, #D02020, #1040C0, #F0C020, strong borders, hard-offset shadows, square geometry, bold typography, asymmetric composition, solid color blocks, and geometric decoration.\n\nNo gradients, glassmorphism, blur, soft generic shadows, or unrelated ecommerce visual system was introduced.\n\n## 10. Reusable section semantics\ncomponents/ui/section-heading.tsx now accepts an optional id and applies it to its H2.\n\nThis lets homepage sections use valid aria-labelledby to H2 relationships without duplicating heading components.\n\n## 11. Accessibility\nSource-level improvements include:\n- one homepage H1\n- explicit IDs for section H2 labels\n- semantic sections\n- native links/buttons\n- existing visible focus styles\n- meaningful product image alt text\n- decorative geometry marked as non-semantic\n- touch-sized CTA/link controls\n- availability represented with text rather than color alone\n- centralized motion system remains responsible for reduced-motion behavior\n- ProductCard product titles changed from H2 to H3 so cards do not create a flat H2 hierarchy beneath each page section\n\nRuntime keyboard, screen-reader, contrast, and reduced-motion checks remain environment-dependent.\n\n## 12. Responsive behavior\nExisting mobile-first layout was preserved for 320, 375, 390, 430, 640, 768, 820, 1024, 1280, 1440, and 1920px widths.\n\nSource behavior covers responsive product, category, and collection grids, wrapping CTA controls, bounded geometry, and readable typography.\n\nActual browser viewport inspection was not executable through the connected GitHub repository integration.\n\n## 13. Performance\nThe homepage remains server-first.\n\nSource review confirms the route is a server component, catalog retrieval is server-side, homepage UI has no use client, no new dependency was introduced, imagery uses Next Image, discovery sets are bounded, populated category/collection checks use canonical relational repository queries, and no homepage-wide client fetch or recommendation engine was added.\n\nThe homepage performs one canonical new-arrival query, one category discovery query, one collection discovery query, and one curated collection product query when a collection exists.\n\nRuntime profiling and Core Web Vitals were not available.\n\n## 14. SEO\nExisting homepage metadata remains the single metadata system:\n- title: 4HRS — Fashion by Design\n- description: Explore the live 4HRS fashion catalog through a bold Bauhaus-inspired storefront.\n- canonical: /\n- robots: index/follow\n- Open Graph title/description/type\n\nNo duplicate metadata system was introduced.\n\n## 15. Data safety\nHomepage presentation continues to consume public storefront DTOs and does not expose supplier/provider metadata, supplier costs, raw inventory quantities, audit information, credentials, synchronization internals, or admin-only fields.\n\nNo direct ORM access exists in homepage UI.\n\n## 16. Testing\nSource-level tests were extended for clear conversion flow, /shop destinations, category/new-arrival/collection sections, removal of the duplicated editorial block, labelled-by section heading relationships, ProductCard H3 hierarchy, unsupported claims, and provider-neutral homepage content.\n\nExisting Phase 4.1 tests continue to cover canonical catalog boundaries, published-only data, deterministic merchandising, canonical routes, empty discovery handling, SEO metadata, image usage, and public data safety.\n\n### Runtime validation limitation\nThe connected GitHub repository integration does not provide an executable shell or browser automation for this repository.\n\nTherefore these commands could not truthfully be reported as executed:\n- npm run lint\n- npm run typecheck\n- npm test\n- npm run build\n\nBrowser smoke, responsive viewport, keyboard, reduced-motion, screen-reader, image-loading, horizontal-overflow, and Core Web Vitals checks also remain runtime-unverified.\n\nNo new runtime failure was observed because runtime execution was unavailable; this is a validation limitation, not a claim that the commands pass.\n\n## 17. Cleanup / phase scope\nPhase 4.2 changes are limited to:\n- components/storefront/homepage.tsx\n- components/ui/section-heading.tsx\n- components/storefront/product-card.tsx\n- lib/storefront/catalog.ts\n- tests/storefront-homepage.test.ts\n- docs/phase-4-2-homepage-conversion-content.md\n\nThe changes clarify CTA copy, consolidate homepage flow, remove duplicate editorial presentation, add a supported brand/value section, make curated discovery independent of an editorial-description requirement, preserve canonical merchandising, add explicit section heading IDs, improve ProductCard heading hierarchy, extend tests, and document validation.\n\nNo unrelated commerce, schema, authentication, payment, order, shipping, or provider refactor was performed.\n\n## 18.
