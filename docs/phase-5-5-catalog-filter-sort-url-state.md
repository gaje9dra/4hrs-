# Phase 5.5 — Production Catalog Filtering, Sorting & URL State Hardening

## Canonical query contract

The shared contract is implemented by `catalogQueryFromSearchParams` and the `CatalogQuery` / `CatalogAppliedQuery` types.

Supported public state:

- category slug
- collection slug
- comma/repeated tag slugs
- tag match mode: `AND` or `OR`
- minimum and maximum price
- in-stock flag
- supported sort
- page
- page size

The same contract is consumed by shop, category, and collection listing routes. Invalid recognized values fail closed before catalog execution.

## Normalization

- slugs are trimmed, lowercased, and validated against the canonical slug grammar
- tags are split from repeated/comma-separated values, deduplicated, and sorted lexicographically
- tag mode is meaningful only when tags are selected; unused `AND` state is removed from URLs
- money values require non-negative values with at most two decimals and are serialized to two decimal places
- price ranges reject minimum values above maximum values using Decimal arithmetic
- page values are positive integers bounded to 10,000
- page size is bounded by the existing catalog maximum of 100
- default sort `newest`, default page 1, default page size 24, `inStock=false`, and tag mode `AND` are omitted from canonical URLs
- unsupported parameters are ignored during canonical serialization rather than becoming catalog state

## Supported filters

The production catalog currently supports only model-backed filters already implemented by the catalog repository:

- category
- collection
- tags with AND/OR semantics
- effective product/variant price
- inventory availability

Variant option values are present in the product model but do not have an existing shared storefront query contract, so Phase 5.5 does not invent a new option-filtering system.

All filtering remains server-side against the published catalog predicate.

## Sorting contract

Supported sorts are:

- newest
- oldest
- price ascending
- price descending
- title ascending
- title descending
- recently updated
- merchandising order for category/collection contexts

Every ordinary product sort adds product ID as a deterministic secondary key. Merchandising order uses canonical category/collection relationship priority:

1. featured
2. priority
3. position
4. product creation time
5. product title
6. product ID

Merchandising sorting is rejected without a category or collection context. No popularity, trending, recommendation, or bestseller sort was introduced.

## URL parameter contract

Canonical URLs are generated by `buildCatalogHref` and `buildCatalogFilterHref`.

Examples:

`/category/shirts?size=m&color=black&sort=price-asc&page=2` is represented only by parameters supported by the catalog contract; unsupported `size`/`color` parameters are not treated as active catalog state unless the architecture is extended to support them.

A normalized example is:

`/shop?tags=graphic%2Cstreetwear&sort=price_desc&page=2`

Default values are removed, tags are deterministic, and filtering URLs reset pagination.

Search routes preserve the existing `q` value while applying shared filter-state changes.

Category and collection pages retain their canonical route context server-side even when their fixed context is not rendered as a removable filter control.

## Pagination interaction

Applying the filter form omits `page`, so a filter change starts at page 1. Individual active-filter removal also omits page. Pagination links use the same canonical serializer and preserve all active filter/sort state.

The repository applies skip/take only after server-side filtering and uses the same filtered predicate for the result count.

## Client/server boundary

Catalog filtering, sorting, counting, and pagination remain server-side. The filter component is a standard GET form plus canonical links for active-filter removal; it does not query the catalog or reconstruct product membership in the browser.

The initial rendered control values come directly from the server-applied query, avoiding a second client query and reducing URL/control hydration drift.

## Filter UX and accessibility

The shared filter component provides:

- labeled category, collection, sort, tag, tag-mode, price, and stock controls
- visible keyboard focus
- 48px-class minimum interactive heights for primary controls
- active-filter links with accessible removal labels
- a clear-all action
- filter submission that resets pagination
- the existing accessible pagination component

Fixed category/collection contexts remain authoritative and cannot be removed by a client control.

## Performance

The existing catalog repository performs filtering and sorting in database queries and counts the same filtered dataset used for pagination. No complete catalog is loaded into the browser.

No new search engine, vector database, external filtering service, or duplicate listing implementation was introduced.

The existing schema has indexes for product status, created time, base price, category/collection merchandising relationships, and option-value relationships. No schema migration was introduced because the current phase did not establish a measured missing-index blocker.

## Testing

Updated shared shop/listing tests cover:

- normalized filters
- deterministic tag serialization
- default-state removal
- malformed recognized parameters
- bounded pagination
- search-state preservation
- filter URL pagination reset

Existing catalog query tests cover price range validation, sort allowlisting, page-size limits, public category/collection/tag resolution, and merchandising context.

The repository's available GitHub integration did not expose runnable workflow results for the final commit, and this environment cannot execute the repository locally. Therefore lint, typecheck, full tests, production build, and browser smoke tests are not claimed as passed.

## Known limitations

- Variant option-value filtering is not exposed because the pre-existing shared catalog query contract does not implement it.
- Browser viewport/back-forward smoke testing requires a runnable browser environment/CI workflow.
- No database index migration was added without a measured query-plan requirement.
